# 출석 정책 다중 적용·반복 관리 전환 계획

## 1. 확정된 목표

- 출석 정책을 `v1`, `v2`처럼 한 정책의 버전으로 관리하지 않는다.
- 부서마다 서로 독립된 여러 출석 정책을 만들고 동시에 활성화할 수 있다.
- 각 정책은 알람처럼 `ON/OFF` 상태를 가진다.
  - `ON`: 설정한 날짜·반복 조건에 해당하면 신규 출석일 생성에 사용한다.
  - `OFF`: 신규 출석일에는 사용하지 않는다.
- 각 정책에서 시간 구간뿐 아니라 적용 시작일·종료일과 반복 조건을 설정한다.
- 정책은 생성·수정·비활성화(삭제)할 수 있다.
- 정책 조건이 같은 부서의 같은 날짜에 겹치면 저장 또는 활성화를 거부한다.

## 2. 핵심 설계 원칙

### 2.1 정책과 출석일의 역할 분리

- `출석 정책`은 이름, 태깅 시작 시각, 정상/지각 단계, 날짜 범위, 반복 조건, 활성 상태를 가진다.
- `출석일`은 특정 날짜에 실제로 적용할 정책과 대상자를 고정한 운영 기록이다.
- 출석일이 만들어진 뒤에는 그 출석일의 정책·대상자·기록을 새 정책 수정으로 바꾸지 않는다.
- 정책 변경은 아직 시작하지 않은 미래 출석일에만 반영한다.

### 2.2 삭제는 이력 보존 방식으로 처리

- 정책을 물리 삭제하지 않는다. `OFF` 또는 `ARCHIVED` 상태로 보관한다.
- 이미 출석일·태깅·정정·감사 로그가 참조하는 정책을 삭제하면 판정 이력이 훼손된다.
- 삭제 요청은 정책을 보관 처리하고, 연결된 미래·미시작 출석일만 취소한다.

### 2.3 충돌은 무조건 거부

- 같은 부서에서 활성 정책 두 개가 같은 날짜에 적용되면 저장·수정·활성화를 거부한다.
- 우선순위, 최근 생성 우선, 임의 선택은 도입하지 않는다.
- 충돌 메시지에는 겹치는 날짜와 기존 정책 이름을 표시한다.
- 이미 생성된 출석일과 새 정책 날짜가 충돌해도 새 정책을 거부한다.

## 3. 데이터 모델 변경

### 3.1 정책 엔터티 전환

- 기존 `attendance_policy_version`의 버전 중심 UI·용어를 제거한다.
- 정책에 다음 정보를 저장한다.
  - 정책 이름
  - 활성 상태: `ON`, `OFF`, `ARCHIVED`
  - 태깅 시작 시각
  - 정책 단계(정상 1개와 지각 1개 이상)
  - 적용 시작일과 선택적 종료일
  - 반복 방식: `ONCE`, `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY`
  - 반복 간격
  - 주간 요일, 월간 날짜, 연간 월·일 조건
  - 생성·수정·비활성화 시각 및 작업 계정

### 3.2 반복 조건과 무결성

- 반복 조건은 정책에 종속된 정규화 테이블로 관리한다.
  - 주간 반복: 선택 요일 집합
  - 월간 반복: 선택 날짜 집합
  - 연간 반복: 월·일 한 쌍
- 적용 시작일은 필수이며 종료일은 선택 사항으로 둔다.
- 종료일은 시작일보다 빠를 수 없다.
- 월간 29~31일은 해당 날짜가 없는 달에 건너뛴다.
- 연간 2월 29일은 윤년에만 적용한다.
- 활성화·수정 시점에는 오늘부터 6개월까지만 실제 출석일을 선생성한다.

### 3.3 마이그레이션과 기존 데이터

- 새 Flyway migration으로 상태·적용 조건·반복 조건 테이블을 추가한다.
- 기존 발행 정책은 `ARCHIVED`로 보관하거나, 실제 미래 출석일에 사용 중인 경우에만 읽기 전용 참조 대상으로 전환한다.
- 기존 `attendance_day.policy_version_id` 참조는 유지해 과거 기록을 보존한다.
- migration은 데이터 삭제나 기존 출석 결과 재판정을 수행하지 않는다.

## 4. 업무 로직 구현

### 4.1 정책 생성과 활성화

1. 입력값과 단계 순서를 검증한다.
2. 반복 조건으로 적용 날짜를 계산한다.
3. 같은 부서의 활성 정책 및 예정 출석일과 날짜 충돌을 검사한다.
4. 충돌이 없으면 정책을 저장하고 `ON` 상태로 활성화한다.
5. 오늘부터 6개월 범위의 미래 출석일과 대상자 snapshot을 만든다.
6. 정책 생성·활성화·출석일 생성을 감사 로그에 남긴다.

### 4.2 정책 수정

1. 과거 또는 진행 중인 출석일은 그대로 유지한다.
2. 수정 전 정책에서 생성한 미래·미시작 출석일만 조회한다.
3. 변경된 반복 조건과 정책 시간으로 충돌을 다시 검사한다.
4. 충돌이 없을 때에만 미래 출석일을 취소·재생성하거나 안전하게 정책을 교체한다.
5. 대상자 snapshot은 정책 수정 시점의 활성 소속 기준으로 새로 만든 날짜에만 생성한다.
6. 변경 전후 값과 영향을 받은 출석일 수를 감사 로그에 남긴다.

### 4.3 ON/OFF 및 삭제

- `ON → OFF`: 미래·미시작 출석일을 취소하고, 과거·진행 중 출석일은 보존한다.
- `OFF → ON`: 충돌 검증 후 미래 출석일을 생성한다.
- 삭제: `ARCHIVED`로 전환한다. 보관된 정책은 다시 활성화할 수 없으며 새 출석일에도 사용하지 않는다.
- 정책을 `OFF` 또는 `ARCHIVED`로 전환하는 작업은 이유 입력을 요구한다.

### 4.4 출석 판정

- 태깅 시에는 해당 날짜에 고정된 출석일의 정책 단계만 사용한다.
- 정책을 나중에 수정·비활성화해도 이전 출석일의 정상·지각·결석 판정은 바뀌지 않는다.
- 한 날짜에 정책이 없으면 태깅을 받지 않는다.

## 5. 화면 개편

### 5.1 정책 목록

- 기존 `vN · 정책명` 목록을 제거한다.
- 정책 카드 또는 표에는 다음을 표시한다.
  - 정책 이름
  - ON/OFF 상태 스위치
  - 적용 기간
  - 반복 요약(예: `매주 월·수·금`, `2026-09-01 ~ 2026-12-31`)
  - 태깅 시작·마감 시각
  - 다음 적용일
  - 수정·보관 버튼
- ON 상태는 초록색, OFF는 회색, ARCHIVED는 별도 보관 상태로 표시한다.

### 5.2 정책 생성·수정 화면

- 한 화면에서 다음을 설정한다.
  - 이름과 ON/OFF 초기 상태
  - 적용 시작일·종료일
  - 반복 없음 / 매일 / 매주 / 매월 / 매년
  - 반복 간격과 요일·날짜·월·일 조건
  - 태깅 시작 시각
  - 정상·지각 단계 추가·삭제와 단계별 종료 시각
- 단계 삭제는 정상 단계 1개와 지각 단계 1개를 항상 남긴다.
- 반복 방식에 따라 필요한 입력만 표시하고, JavaScript 없이도 서버 검증과 재표시가 가능해야 한다.
- 충돌 시 기존 정책명·충돌 날짜를 포함한 오류를 폼에 표시하고 입력값을 보존한다.

### 5.3 출석 날짜 화면

- 수동으로 정책과 날짜를 조합해 생성하는 기존 입력 폼은 제거한다.
- 정책이 생성한 실제 출석일 목록과 상태·정책·대상자·기록만 표시한다.
- 개별 출석일의 취소·대상자 관리·수동 정정 기능은 유지한다.

## 6. API·권한·감사

- 정책 생성, 수정, ON/OFF, 보관은 해당 부서의 관리자만 실행할 수 있다.
- 모든 조회·변경은 URL의 `departmentId`와 정책 소유 부서를 함께 확인한다.
- 다른 부서의 정책 ID를 추측해 호출하면 존재 여부를 노출하지 않고 `404`로 처리한다.
- 다음 이벤트를 감사 로그에 남긴다.
  - 정책 생성
  - 정책 수정
  - 활성화·비활성화
  - 보관
  - 충돌 거부
  - 미래 출석일 생성·취소
- 모든 변경은 PRG와 CSRF 보호를 사용한다.

## 7. 테스트 계획

### 7.1 도메인·서비스 테스트

- 단발, 매일, 매주, 매월, 매년 반복 날짜 계산
- 윤년, 월말, 존재하지 않는 월간 날짜
- 정상 1개·지각 1개 이상, 종료 시각 오름차순 검증
- ON/OFF와 ARCHIVED 상태 전이
- 정책 수정이 과거·진행 중 출석일을 변경하지 않는지 검증

### 7.2 충돌 테스트

- 동일 날짜 단발 정책 두 개 거부
- 주간·월간·연간 반복이 한 날짜라도 겹치면 거부
- OFF 정책은 충돌 대상에서 제외
- OFF 정책 활성화 시 기존 ON 정책과 겹치면 거부
- 기존 예정 출석일과 새 정책의 날짜 충돌 거부
- 다른 부서의 같은 날짜 정책은 허용

### 7.3 웹·보안·통합 테스트

- 정책 생성·수정·ON/OFF·보관 화면과 성공·오류 메시지
- 충돌 후 입력값 보존
- 미래 출석일 생성·취소 및 대상자 snapshot
- 과거 출석 기록·감사 로그 보존
- 다른 부서 정책에 대한 IDOR 차단
- PostgreSQL Testcontainers에서 Flyway migration과 모든 제약 검증

## 8. 완료 기준

- 부서 관리자가 여러 정책을 독립적으로 생성하고 ON/OFF 할 수 있다.
- 각 정책에 날짜와 반복 조건을 설정할 수 있다.
- 활성 정책의 적용 날짜가 하나라도 겹치면 저장 또는 활성화되지 않는다.
- 정책 수정·비활성화·보관이 과거 출석 기록을 바꾸지 않는다.
- 미래 출석일만 정책 변경에 맞춰 안전하게 갱신된다.
- 정책·출석일·반복·충돌·IDOR 관련 자동 테스트가 모두 통과한다.
